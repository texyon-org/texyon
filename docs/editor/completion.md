# Completion from the engine's own macro table

A design note, not an implementation. The editor's completion currently knows
what the *project* declares — labels, citation keys, and the commands its own
preamble defines — plus a short hand-written list of common LaTeX commands.
What it does not know is what its **packages** define, and the usual ways of
finding that out are all worse than one available here.

## What other editors do

- **LaTeX Workshop** ships `data/packages/*.json`: a few hundred packages,
  generated by scraping `.sty` files and then curated by hand.
- **TeXLab** bundles a completion database generated from a TeX Live tree.
- **digestif** parses `.sty` files at runtime.
- **`texdef`** does not parse at all — it runs TeX and reports `\meaning\foo`.
  Correct, but one command per invocation and a fresh run each time.

Every one of those is either an approximation made from outside the engine, or
a snapshot that goes stale. They have no alternative: they do not own a TeX.

## What is available here instead

After a document's preamble has run, TeX's hash table *is* the answer, and in
this codebase that table is a Rust data structure: `EqtbState` holds it as
`hash_s0`/`hash_s1`, names in the string pool, meanings in `eqtb`. For a macro,
the parameter text carries the arity and any delimiters — the same thing
`\meaning` prints, read directly rather than through a round trip.

Walking it gives, for the document actually open, with its packages and its
options:

- every command that exists, including ones no scanner could see — generated in
  loops, built with `\csname`, made conditional on a package option, or
  redefined by something loaded later;
- true arity, so a completion can insert the right number of `{}` to tab
  through;
- xparse signatures where the definition used them. `\NewDocumentCommand{\foo}{s
  m O{d}}` stores `s m O{d}`, so optional-versus-mandatory, star variants and
  defaults are all recoverable, not just a count;
- environments, which are `\foo`/`\endfoo` pairs in the same table.

It fits the existing architecture: the preamble is already checkpointed, so the
table only needs recomputing when the preamble changes, and the replay machinery
already knows when that is.

## What it cannot give

- **Argument names.** TeX stores a parameter text — `#1#2` — and a body. There
  is no slot where "numerator" could live, so nothing is being lost: the
  information was never created. Names exist only in documentation.
- **Provenance.** TeX does not record which file defined a macro, so "this comes
  from amsmath" is not in there. A static scan of `.sty` files answers that, and
  is therefore complementary rather than redundant.

## Key-value options are the exception worth noting

For positional arguments there are no names, ever. For key-value options there
are real ones, and they are stored as control sequences:

    \define@key{Gin}{width}{\def\Gin@ewidth{#1}}
    \define@key{Gin}{height}{\def\Gin@eheight{#1}}

So `\KV@Gin@width` is in the macro table like anything else, and the key surface
of `graphicx`, `hyperref`, `geometry` and `tikz` — the part nobody remembers —
is recoverable.

One catch: the table knows that a family named `Gin` has a key named `width`. It
does not know that `\includegraphics` *reads* family `Gin`, because that lives in
whatever calls `\setkeys{Gin}{…}` rather than in any macro's definition. Mapping
keys to the command that accepts them needs a static scan or a small curated
table.

## Honest accounting

The data is nearly free. The product is not.

Recall is not what makes completion feel good — ranking is. Offering two
thousand commands for `\se` is worse than offering thirty, which is exactly why
the curated lists elsewhere are small on purpose. A walk of the macro table
solves recall completely and leaves precision entirely untouched: prefix over
fuzzy, project-defined above package-defined, recently-used above never-used,
and a cutoff.

Rough split: the walk is perhaps 15% of the effort and 40% of the felt
improvement. The rest is ordinary editor work — ranking, placeholder insertion,
key-to-command mapping — and it is easier to build once there is a real set to
rank.

## What the field actually does

Surveyed 2026-07. Four approaches are in use, and they divide along one line:
whether the data comes from outside the engine or from inside it. Everyone is
currently outside.

### The CWL corpus, and why it cannot be used here

**TeXstudio** maintains the only comprehensive machine-readable description of
LaTeX commands that exists: 4,449 `.cwl` files, 10.3 MB, in its `completion/`
directory. The format began in Kile and TeXstudio extended it. It carries
considerably more than command names:

    \begin{alignat}[alignment]{ncols}#\math,array
    \AmSfont#*
    width=##L
    keepaspectratio#true,false
    scale=%<factor%>
    page=%<page number%>

That is: named arguments (`alignment`, `ncols`), key names with value *types*
(`##L` is a length), enumerated values, human-readable placeholders
(`%<factor%>`), a "rarely used" marker (`#*`), and context classification
(`#\math,array` means valid only in maths or an array). It answers the argument-
name question that the engine cannot.

**It is GPL-3.0**, because TeXstudio is. This project is MIT. The corpus cannot
be vendored, converted, or derived from without relicensing.

**LaTeX Workshop is MIT and vendors it anyway** — `dev/getcwl.sh` downloads
TeXstudio's `completion/` directory and `dev/parse-cwl.ts` converts it into
`data/packages/*.json`. Whether that is defensible is their problem; it is not
a precedent to copy.

### The others

- **TeXLab** indexes the `.sty` files of the packages a document actually uses,
  as it types — dynamic, no bundled corpus.
- **TeXstudio**, when it has no `.cwl` for a package, generates one by parsing
  the `.sty`. So static extraction is a proven fallback, not a theory.
- **LaTeX Workshop** also mines the TeX Live package database
  (`texlive.tlpdb`) and CTAN for package and class *names and descriptions* —
  a clean, permissively-licensed source for that narrower question.

Nothing found reads the engine's macro table. The approach above appears to be
unexplored, for the ordinary reason that no other editor ships a TeX.

## Ranking is the real problem, and Overleaf measured it

Overleaf published what happened when they took autocomplete seriously
(*A Data-Driven Approach to LaTeX Autocomplete*). They started with fuzzy
matching, found it insufficient because it ignores how common a command is, and
mined roughly 8,000 documents from their gallery — about 15,000 distinct
commands over 900,000 uses. What they learned is directly reusable:

- **Weight by the number of documents a command appears in, not by raw count.**
  Raw counts are dominated by a few documents that use one command a thousand
  times.
- **Track median uses per document**, so single-use commands like
  `\begin{document}` stop being suggested after the once they are wanted.
- **Context dominates.** `\section` and `\chapter` essentially never appear
  before `\begin{document}`; `\item` belongs to list environments;
  `\includegraphics` to figures. Suggesting by position is worth more than
  suggesting more.
- What they shipped: the **top hundred** commands plus whatever the document
  already uses.

The corpus is the part not reproducible here — but note the second half of that
sentence. Commands the document already uses need no corpus at all, and an
editor that keeps a user's projects can rank by *their* usage, which beats a
global average for anyone past their first document.

## Suggested order

1. An engine entry point that walks the table and returns user-facing entries
   with arity and signature, filtering internals (`@`, `\l__`, `\g__`, `\c__`).
   Cache it against the preamble checkpoint.
2. A ranker in the client, over that set plus what the project declares.
3. Key-to-command mapping, from a static scan of the packages in use.
4. Curated argument names for the few dozen commands where they earn their
   place.
